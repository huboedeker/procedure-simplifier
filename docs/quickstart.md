# Operating a real run

1. Install the package and export the framework to a writable workspace with `procedure-simplifier export-framework ./framework`. Keep inputs and `./runs` outside version control. Never write into the installed package.
2. Save the exact user request. Initialize the audit directory with `procedure-simplifier audit init ./runs case-001 ./request.txt`. Capture sources using `audit capture ./runs/case-001 source ./input.pdf`. Read returned artifact IDs; do not invent them.
3. Inspect source structure and rendered pages, including figures and scope boundaries. Resolve material gaps in audience, intent, permitted omissions and protected requirements. Use the conversation's already-settled choices. Record new answers as user_input artifacts.
4. Fill exported `templates/approach.json`: output role, outcome, scope, eight switches, decision provenance, authority, success criteria, framework version, skill target and processing plan. Templates are deliberately invalid until populated. Do not submit the blank template as a completed task.
5. Check context capacity and create a chunk plan even for a single coherent packet. Validate with `procedure-simplifier chunks plan.json`; capture the plan/check and link it from the task. Original-source completeness and actual model capacity require inspection/host knowledge; passing plan metadata is not a measurement of either.
6. Save the approach with `procedure-simplifier audit approach ./runs/case-001 ./approach.json`, then `audit stage ./runs/case-001 analysis`. The current approach helper checks switches and material gaps but does not automatically validate processing.plan_ref; the coordinator must perform that handoff check.
7. Run the analyst against original evidence, construct the source manifest, structured units, dependencies, scenarios, visual inventory and substantive-change impact cards. Independently inspect original relevant pages before using the analyst map as the review checklist.
8. Run the simplifier within the task settings. Before any reviewer reads the draft, capture it immutably and send that exact path/hash. Later edits use new versions. Reviewer findings and rechecks remain separate records. Parallel workers have separate directories and one journal writer.
9. Validate the transformation and quality records with `procedure-simplifier validate run.json` and `procedure-simplifier quality quality.json run.json`. Quality file paths resolve relative to quality.json. Verify actual delivered-file/task/source hashes, render the chosen output format and inspect visual/text meaning independently.
10. Compute reduction from exact registered files with `procedure-simplifier metrics baseline.txt output.md`. Document included/excluded scope; no token, cost, image or labor percentage is implied. Stage completed metadata alone is not a complete comparison study.
11. Create the readable closing summary plus structured summary, validation and delivery records. Complete learning.json; apply justified reusable changes with before/after snapshots, review, checks and rollback, or record deferred/rejected/no-change decisions.
12. Capture records with their artifact kinds and `--parents` links. Record `audit stage ./runs/case-001 closed`, then `audit verify ./runs/case-001`. The local gate closes proposal handover; it cannot verify real human adoption authority or approve a policy. Full approved-delivery verification remains future integration work.

Use individual command help, for example `procedure-simplifier audit capture --help`. Narrative handoffs/failures/decisions are recorded through the audit module's `append()` API. The CLI does not automatically observe host calls. Review the exported detailed contracts before making claims about coverage or quality.
